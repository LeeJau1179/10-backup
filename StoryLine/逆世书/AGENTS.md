# 写作库规范（逆世书）

## 创作分层规则（Codex / Scene / 正文）

- **Codex（设定层）**：角色、地点、组织、体系等设定条目 = 权威内容。Codex 词条只做外部引用，**禁止**引入或掺入 Scene 层的具体剧情内容。
- **Scene（修饰层，场景卡）**：引入并调用 Codex 的设定规则；正文、草稿的具体内容来源于 Scene 层的各项内容。
- **正文、草稿（成果层）**：最终产出文字，由 Scene 层驱动生成。

**修改同步铁律**：除非特别说明，任一层的修改都需**双向**同步修正——Codex 改动要检查 Scene / 正文是否需跟改；写 Scene 或正文时发现设定问题，也要回溯修正 Scene 乃至 Codex。任何一层改动都要上下联动核查。

**冲突判定铁律**：Codex 与 Scene／正文冲突时，**Codex 即答案，正文即错误**：登记到该场 SceneNotes「正文待改」，不在场景卡和笔记里重复写 Codex 口径；不得写成"两处口径并存，待作者裁定"去反问作者。只有当 Codex 本身尚未规定（如剧情排期未定）时，才允许挂 TODO 等裁定。

**正文与场景卡、SceneNotes 冲突**：以场景卡和 SceneNotes 为准——那是作者现行方案，包括还没落到正文的改动。作者也会直接手改正文，所以改正文前先把冲突逐条列给作者（卡或笔记写什么、正文写什么），确认后再改。

**单一事实源总原则**：同一个事实，全库只允许在一个主场文件里写全；其余位置一律用 wikilink 指过去，不得复述。执行细节见 `[[Codex/AGENTS]]`。

## 场景卡（Scene）三件套

每张场景卡 frontmatter 必含以下三字段：

```yaml
---
type: scene
title: 陪读方案·苏晚身份材料齐备        # 无号标题（唯一，链接用它）
aliases: ["陪读方案·苏晚身份材料齐备"]  # 与 title 完全相同
sequence: 48                           # 数字，仅用于排序
---
```

- 文件名 = `NN-NN 无号标题.md`，如 `01-48 陪读方案·苏晚身份材料齐备.md`
- 文件名的数字前缀**只用于文件树排序**，可随时改；`title` / `aliases` 不随数字变。

## 链接铁律：场景不加链接

- 提到场景一律写纯文字标题，用「」括起，如「陪读方案·苏晚身份材料齐备」，不加 `[[ ]]`。Obsidian 只按文件名解析链接，场景文件名带序号，StoryLine 改标题时也会重新加序号，场景链接指不到文件。
- 例外：frontmatter 的 `setup_scenes`／`payoff_scenes` 是 StoryLine 插件字段，照旧写 `"[[无号标题]]"`。
- wikilink 只用于 Codex 词条（人物、地点、物品、组织、设定）。

## 增删 / 改序

- 只改两处：**文件名数字** + `sequence` 字段
- `title`、`aliases` **一律不动**
- 拖拽重排由 StoryLine 插件自动完成（触发全局重排 + 顺延序号）；手动改序同样只动数字 + `sequence`

## 新建场景 SOP（agent 执行）

1. 写完整 frontmatter：三件套 `title`（无号、唯一）/ `aliases`（= title）/ `sequence`，加 `act`、`storyDate`、`chapter`、`pov`、`characters`、`location`、`status`、`subthread` 等。
   - 所属故事线 **必填**：使用 `subthread` 列表填写该 Scene 实际归属的一条或多条故事线，不得缺省或留空。
2. `synopsis`、`conflict` **必写**，写法见下方「场景卡与 SceneNotes」。
3. SceneNotes **必写**，只含 `## 节拍`、`## 边界`、`## 正文待改` 三节，内容可留空。
4. `sequence` 用 **`+0.5` 占位**：要插在 `seq N` 与 `seq N+1` 之间，填 `N.5`，文件名 `NN-N.5 标题.md`。
   - 例：插在 `02-85` 与 `02-86` 之间 → `sequence: 85.5`，文件名 `02-85.5 标题.md`
5. 建完**提醒用户去 UI 拖一下**：插件 `globalResequence` 会把全书 `sequence` 归整成连续整数、后续序号自动顺延（只动 frontmatter，不动 title/aliases/链接）。
6. 归整只发生在「手动拖动/重排」时；UI 自动扫描不会归整，所以建完必须提醒。
7. **插件不改文件名**（StoryLine 1.10.82 实测：重排只写 `sequence`，只有改 title 时才重命名文件）。用户拖完并同步后，agent 须按各卡 `sequence` 把文件名前缀改成 `<幕两位>-<sequence两位起> 标题.md`，并同步更新 `今生/System/plotgrid.json` 等 JSON 里的场景路径。

## 场景卡与 SceneNotes（铁律）

| 位置 | 写什么 |
| --- | --- |
| 场景卡 `synopsis` | 这场发生了什么、改变了什么，一两句 |
| 场景卡 `conflict` | 这场的矛盾（戏剧张力是什么），一句话 |
| 场景卡 `setup_scenes`／`payoff_scenes` | 伏笔、铺垫与兑现关系，两边都写 |
| SceneNotes `## 节拍` | 关键节拍 |
| SceneNotes `## 边界` | 本场硬约束 |
| SceneNotes `## 正文待改` | 方案已改、正文还没跟上的地方（常驻） |

- **synopsis**：结果导向，不写怎么发生、谁先开口、怎么收尾。
- **conflict**：只写矛盾，不复述事件经过。
- **节拍**：只写对剧情确实重要、不能随意改变的事件顺序。每条一句，不写动作、神态、道具和措辞；后面场次要呼应的关键台词可保留原句。这场最该写足的一条，末尾标「（重点）」，只标一条。没有就留空。
- **边界**：只写违反后会造成实际逻辑错误的客观条件，如必须在变身冷却结束后发生。没有就留空。
- **正文待改**：常驻小节。场景卡或笔记改了、正文还没跟上，或正文与 Codex 冲突时，逐条写正文要改成什么。正文改完就删掉对应条目，小节留空保留。
- **状态**：正文有修改（新写、重写、清理、按正文待改修改），该场 `status` 改为 `written`。
- SceneNotes 只有这三节，不加其他小节；场景关系只登记在 setup／payoff 字段，不用文字重复。

  ```markdown
  ## 节拍

  - 苏晚回到宿舍，碰见正在开门的王倩。
  - 两人一起进屋。
  - 舍友互相介绍。（重点）

  ## 边界

  ## 正文待改
  ```

- 不写：修改历史、方案比较、错误纠正、解释性描述、写法建议（当时为改某个问题提的局部建议）、能从 Codex 或前后场推出的约束。否定旧方案（如「不要让王倩已经进屋」「不要重复介绍王倩」）不是边界。
- 拿不准该不该留的内容，条目末尾标「（待审）」，不擅自删改。
- 修改时直接改成最新方案，不留痕迹。

## 写作注意事项

- 性别代词"他／她"须随人物当前形态、所指身份及叙述情境调整，不得固定沿用。身份切换、回忆及人物对白中，应核对实际所指；对白中的代词须符合说话者当时的认知。
- 不在正文叙述中复述设定规则（变身冷却、共身传导、身份限制等），也不写"男身／女身"这类设定术语；规则由动作、体感和行为后果自然呈现，不向读者解释，也不替主角复述他早已知道的事。
- 不写"以为／可能／兴许"式猜测腔让读者去解读；主角的判断以确定语气直写，哪怕判断是错的（如"那天泡了海水。落的病。"），误判本身就是伏笔。

## 通用 Obsidian 铁律

- 表格内 wikilink 的 `|` 显示名分隔符必须转义为 `\|`（避免被解析成列分隔符）
- 人物名必须用 wikilink，禁止裸写（如 `裴衍` 应写 `[[裴衍]]`）

## AI 沟通标准

- 回复简短、高效；除非用户主动询问或明确要求详细说明，否则拒绝长篇解释。
- 回复用户消息时，禁止只发送编号、序号或仅有标题。引用、确认或选择某一项时，必须同时写明对应的标题和关键内容，使该回复脱离上文也能看懂具体所指，无需用户根据序号回查上下文。
- 回答任何涉及序号、编号、标号或排序的问题前，必须核查当前文件或系统中的真实记录，不得凭记忆、旧对话或原有顺序推定。新增、删除或重排内容后，后续编号可能已经变化，必须以核查时的最新记录为准。
