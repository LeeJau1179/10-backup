# 写作库规范（逆世书）

## 创作分层规则（Codex / Scene / 正文）

- **Codex（设定层）**：角色、地点、组织、体系等设定条目 = 权威内容。Codex 词条只做外部引用，**禁止**引入或掺入 Scene 层的具体剧情内容。
- **Scene（修饰层，场景卡）**：引入并调用 Codex 的设定规则；正文、草稿的具体内容来源于 Scene 层的各项内容。
- **正文、草稿（成果层）**：最终产出文字，由 Scene 层驱动生成。

**修改同步铁律**：除非特别说明，任一层的修改都需**双向**同步修正——Codex 改动要检查 Scene / 正文是否需跟改；写 Scene 或正文时发现设定问题，也要回溯修正 Scene 乃至 Codex。任何一层改动都要上下联动核查。

**冲突判定铁律**：Codex 与 Scene／正文冲突时，**Codex 即答案，正文即错误**：登记到该场 SceneNotes「正文待改」，不在场景卡和笔记里重复写 Codex 口径；不得写成"两处口径并存，待作者裁定"去反问作者。只有当 Codex 本身尚未规定（如剧情排期未定）时，才允许挂 TODO 等裁定。

**正文与场景卡、SceneNotes 冲突**：以场景卡和 SceneNotes 为准——那是作者现行方案，包括还没落到正文的改动。作者也会直接手改正文，所以改正文前先把冲突逐条列给作者（卡或笔记写什么、正文写什么），确认后再改。

**单一事实源总原则**：同一个事实，全库只允许在一个主场文件里写全；其余位置一律用 wikilink 指过去，不得复述。执行细节见 `[[Codex/AGENTS]]`。

## 场景卡（Scene）必填字段

每张场景卡 frontmatter 必含以下两字段：

```yaml
---
type: scene
title: 陪读方案·苏晚身份材料齐备        # 无号标题（唯一，链接用它）
sequence: 48                           # 数字，仅用于排序
---
```

- 文件名 = `NN-NN 无号标题.md`，如 `01-48 陪读方案·苏晚身份材料齐备.md`
- 文件名的数字前缀**只用于文件树排序**，可随时改；`title` 不随数字变。

## 链接铁律：场景链接指向带序号的文件名

- 提到场景用 wikilink 指向场景文件的**当前文件名（含序号）**，显示名写无号标题：`[[01-48 陪读方案·苏晚身份材料齐备|陪读方案·苏晚身份材料齐备]]`（表格内写 `\|`）。
- 写链接前先按 `title` 查到当前文件名。只写 `[[无号标题]]` 是断链：Obsidian 只按文件名解析。
- 序号变化后由前缀同步插件调用 Obsidian 改名接口更新文件名及链接，须开启自动更新内部链接（见下方「新建场景 SOP」）。
- 例外：frontmatter 的 `setup_scenes`／`payoff_scenes` 是 StoryLine 插件字段，照旧写 `"[[无号标题]]"`。

## 增删 / 改序

- 手动改序只改 `sequence` 字段，文件名数字由 `storyline-prefix-sync` 插件同步。
- `title` **不动**
- 拖拽重排由 StoryLine 插件自动完成（触发全局重排 + 顺延序号），文件名前缀由同步插件处理。

## 新建场景 SOP（agent 执行）

1. 可直接新建场景文件，按下列要求写完整 frontmatter 并核查插件识别结果：`title`（无号、唯一）、`sequence`，加 `act`、`storyDate`、`chapter`、`pov`、`characters`、`location`、`status`、`tags` 等。
   - `tags` 记故事线（StoryLine 故事线视图读这个字段），与 `characters`、Arc Point 各司其职：
     - `characters`：谁在场，出场即登记，交由人物视图检查出场分布与间隔。
     - `主线`：每场都挂，排第一。全书只有这一条主线，作为各支线的参照。
     - Arc Point（frontmatter `arcAnchor: true`，场景检查器里的「弧点」）：只标主线节点，即本场让主角在本卷主轴上往前走了一步；其他线的转折不标。
     - 其余标签都是支线，直接以人物、群体或事务命名。每场按本场实际推进挂一到两条，主要归属紧跟 `主线`；确有三条独立推进可挂三条；本场没有支线推进就只挂 `主线`。
       - 判定边界：此人或此事的目标、行动、认知、处境，或与主角的关系有推进。人物独自行动（主角不在场，如[[林北川]]查线索、[[王倩]]买卖信息）也计入。背景、场合、普通提名不算推进；看其电影、引用旧照片、借用其物品不自动挂线。
       - 人物：`林硕`、`周扬`、`林北川`、`林岚`、`苏然`、`一伶`（系统以人的面目出现或独立行动时）、`王倩`、`郑伟`、`陈思思`、`陆潇`、`李曼`、`叶宁`、`周海`、`程辉`。
       - 群体：`许家`（[[许国栋]]、[[苏文君]]）、`苏家`（[[沈如兰]]、[[苏正鸿]]及苏家兄弟）、`室友`（[[孟夏]]、[[顾盼]]）、`滨海圈`（[[王屿]]、[[裴衍]]、[[陈序]]）。
       - 事务：`学业`（课程、成绩、专业学习）、`事业`（清债、工作、兼职、摄影、公司）、`系统`（规则与限制、任务阶段、卡种、异常回应）。
       - 人物有需追踪的行动与后果时按需扩展。
     - 支线要有头有尾：每条支线在本卷有起点、经过和阶段结果；只为后续卷埋设的伏笔线不要求本卷收束。检查遗漏时逐条看支线的头尾；出场间隔和轨道空白只提示检查，不等于剧情缺漏。
   - `系统`在新卡种首次出现、机制或限制变化、系统异常回应时挂；同类卡重复发放和使用既有能力不挂。`一伶`另行判断；姐姐的临时分身与经验归集不算妹妹独立行动。
   - 标签调整保留无关标签与内容，不改正文、标题、序号、日期及状态；核对场景数量和轨道关联。故事线说明只给 `主线` 写，存于 `今生/System/plotlines.json`；StoryLine 运行时以内存中的说明为准并会写回该文件，须在 Obsidian 关闭时修改。
2. `synopsis`、`conflict` **必写**，写法见下方「场景卡与 SceneNotes」。
3. SceneNotes **必写**，只含 `## 节拍`、`## 边界`、`## 正文待改` 三节，内容可留空。
4. `sequence` 用 **`+0.5` 占位**：要插在 `seq N` 与 `seq N+1` 之间，填 `N.5`，文件名 `NN-N.5 标题.md`。
   - 例：插在 `02-85` 与 `02-86` 之间 → `sequence: 85.5`，文件名 `02-85.5 标题.md`
5. 建完**提醒用户去 UI 拖一下**：插件 `globalResequence` 会把全书 `sequence` 归整成连续整数、后续序号自动顺延（只动 frontmatter，不动 title 和链接）。
6. 归整只发生在「手动拖动/重排」时；UI 自动扫描不会归整，所以建完必须提醒。
7. **文件名前缀由本地插件 `storyline-prefix-sync` 自动同步**（`.obsidian/plugins/storyline-prefix-sync/`）。StoryLine 1.10.81 起重排只写 `sequence`、不改文件名；本插件在 `act`／`sequence` 变化约 2 秒后，用 Obsidian 改名接口把前缀改成 `<幕两位>-<sequence两位起> 标题.md`，全库链接随之自动更新。
   - agent **不再手动改前缀**，改序只改 `sequence`。Obsidian 必须开着，插件才会触发；没开就停下报告，不得退回 shell 改名。
   - 一次改名超过 20 个时插件会弹窗列清单，需用户在 Obsidian 里点确认；agent 提醒用户确认，不得绕过。
   - 插件跳过：没有序号前缀的文件、文件名标题 ≠ `title` 的文件（如带 ` (1)`）、Archive。拖完后用命令「检查场景文件名前缀（只看不改）」核对，被跳过的报告给用户，不要自行改名绕过。
   - `plotgrid.json` 的 `linkedSceneId` 与 corkboard 位置由 StoryLine 随改名自动更新，但**只限当前打开的项目**。改了非当前项目（如在今生打开时改初世）的 `sequence` 后，须核查该项目 `System/*.json` 里的场景路径是否都存在，有失效的报告给用户。

## 场景卡与 SceneNotes（铁律）

| 位置 | 写什么 |
| --- | --- |
| 场景卡 `synopsis` | 这场发生了什么、改变了什么，一两句 |
| 场景卡 `conflict` | 这场的矛盾（戏剧张力是什么），一句话 |
| 场景卡 `setup_scenes`／`payoff_scenes` | 伏笔、铺垫与兑现关系，两边都写 |
| SceneNotes `## 节拍` | 关键节拍 |
| SceneNotes `## 边界` | 本场硬约束 |
| SceneNotes `## 正文待改` | 方案已改、正文还没跟上的地方（常驻） |

- **synopsis**：结果导向，不写怎么发生、谁先开口、怎么收尾。
- **conflict**：只写矛盾，不复述事件经过。
- **节拍**：只写对剧情确实重要、不能随意改变的事件顺序。每条一句，不写动作、神态、道具和措辞；后面场次要呼应的关键台词可保留原句。这场最该写足的一条，末尾标「（重点）」，只标一条。没有就留空。
- **边界**：只写违反后会造成实际逻辑错误的客观条件，如必须在变身冷却结束后发生。没有就留空。
- **正文待改**：常驻小节。场景卡或笔记改了、正文还没跟上，或正文与 Codex 冲突时，逐条写正文要改成什么。正文改完就删掉对应条目，小节留空保留。
- **状态**：正文有修改（新写、重写、清理、按正文待改修改），该场 `status` 改为 `written`。
- SceneNotes 只有这三节，不加其他小节；场景关系只登记在 setup／payoff 字段，不用文字重复。

  ```markdown
  ## 节拍

  - 苏晚回到宿舍，碰见正在开门的王倩。
  - 两人一起进屋。
  - 舍友互相介绍。（重点）

  ## 边界

  ## 正文待改
  ```

- 不写：修改历史、方案比较、错误纠正、解释性描述、写法建议（当时为改某个问题提的局部建议）、能从 Codex 或前后场推出的约束。否定旧方案（如「不要让王倩已经进屋」「不要重复介绍王倩」）不是边界。
- 拿不准该不该留的内容，条目末尾标「（待审）」，不擅自删改。
- 修改时直接改成最新方案，不留痕迹。

## 写作注意事项

- 性别代词"他／她"须随人物当前形态、所指身份及叙述情境调整，不得固定沿用。身份切换、回忆及人物对白中，应核对实际所指；对白中的代词须符合说话者当时的认知。
- 不在正文叙述中复述设定规则（变身冷却、共身传导、身份限制等），也不写"男身／女身"这类设定术语；规则由动作、体感和行为后果自然呈现，不向读者解释，也不替主角复述他早已知道的事。
- 不写"以为／可能／兴许"式猜测腔让读者去解读；主角的判断以确定语气直写，哪怕判断是错的（如"那天泡了海水。落的病。"），误判本身就是伏笔。

## 通用 Obsidian 铁律

- 表格内 wikilink 的 `|` 显示名分隔符必须转义为 `\|`（避免被解析成列分隔符）
- 人物名必须用 wikilink，禁止裸写（如 `裴衍` 应写 `[[裴衍]]`），全库适用

## AI 沟通标准

- 回复简短、高效；除非用户主动询问或明确要求详细说明，否则拒绝长篇解释。
- 回复用户消息时，禁止只发送编号、序号或仅有标题。引用、确认或选择某一项时，必须同时写明对应的标题和关键内容，使该回复脱离上文也能看懂具体所指，无需用户根据序号回查上下文。
- 回答任何涉及序号、编号、标号或排序的问题前，必须核查当前文件或系统中的真实记录，不得凭记忆、旧对话或原有顺序推定。新增、删除或重排内容后，后续编号可能已经变化，必须以核查时的最新记录为准。
