# 写作库规范（逆世书）

本文件是写正文与改场景的**高频主入口**。全库通用铁律（局部改稿、讨论≠设定、改文件不留痕、改名走 Obsidian）见根目录 `AGENTS.md`；新建场景、改序、`tags` 故事线与插件同步见 [[场景管理SOP]]。

## 创作分层与冲突判定

- **三层分工**：**Codex（设定层）**＝权威设定，只被外部引用，**禁止**掺入具体剧情；**Scene（场景卡 + SceneNotes）**＝现行方案层，调用 Codex 驱动正文；**正文**＝最终成果层。
- **双向同步**：任一层修改都须上下核查——改 Codex 检查 Scene／正文是否跟改；写正文发现设定问题同步回溯修正 Scene 乃至 Codex。
- **Codex vs Scene／正文冲突**：**Codex 即答案，正文即错误**。登记到该场 SceneNotes「正文待改」，不在卡或笔记里复述 Codex 口径，不反问作者“待裁定”。只有 Codex 本身未规定时，才允许挂 TODO 等裁定。
- **正文 vs 场景卡／SceneNotes 冲突**：以场景卡和 SceneNotes 为准。因作者也会手改正文，动手改正文前先把冲突逐条列给作者（卡／笔记写什么 vs 正文写什么），确认后再改。
- **单一事实源**：同一事实全库只在一处主场文件写全，其余位置用 wikilink 指路，不复述。细节见 [[Codex/AGENTS]]。

## 写正文 SOP（高频必执行）

### 1. 写前必读（按序核对）

1. 本场场景卡与对应 `SceneNotes`（节拍、边界、正文待改）；
2. 紧邻的**上一场、下一场正文**（核对时间衔接、动作落点、人物当前认知与称呼）；
3. 出场人物卡与涉及设定（`Codex/`），卷二核对 [[卷二 大一课表]] 与当阶段排期；
4. [[写作风格]] 与 [[AI 语录]]「🔴 高频红线」。

### 2. 正文写作硬约束

- **活人口语，禁书面金句**：人物怎么说话就怎么写，不写对仗排比、金句点评和感悟总结；熟人聊天允许自然短来回，不把一轮互动压成塞满信息的单句。细则与对照例见 [[写作风格]]。
- **不解释、不写设定腔**：不在正文复述设定规则（冷却、共身、身份限制等），禁用“男身／女身”等设定术语；规则由动作、体感和后果自然呈现，不替主角复述他早知道的事。
- **直写判断，不写猜测腔**：不用“以为／可能／兴许”让读者去猜；主角判断以确定语气直写，哪怕是错判（如“那天泡了海水。落的病。”），误判本身就是伏笔。
- **性别代词随境调整**：“他／她”随人物当前形态、所指身份和叙述情境变化，不得固定沿用；对白中的代词须符合说话者当时的认知。
- **正文人名与代词自然切换**：出现人物全名时写 `[[姓名]]`（口语称谓／长辈称呼按需用 `[[周海|老周]]`、`[[苏文君|妈]]`）；同一人物连续动作或语境清晰时，正常用“他／她”或承前省略，禁止为防裸写满屏重复 `[[人名]]`。非正文文件（Codex、SceneNotes、大纲、表格）人名一律用 `[[姓名]]`，表格内 `|` 转义为 `\|`。

### 3. 交付前自检清单（逐条过完再交付）

1. **信息差**：每句台词和问句，说话人当下有途径知道吗？没途径就改问句或删。
2. **常识与衔接**：场所结构、时代（2005–2007）、领域常识与前后场时间、细节都对得上吗？
3. **去 AI 味**：有没有书面金句、总结升华、空镜头暗示、心理过度解释、流水账动作、群体轮流笑？
4. **对话闭环**：每个话头有合理落点吗？删掉旧前提后，衍生回应和承诺都清干净了吗？
5. **红线复核**：对照 [[AI 语录]]「🔴 高频红线」逐条核查一遍。

### 4. 快照留存与状态更新

- 写出初稿时顺手留存基线快照（不侵入正文），供作者改稿后用 `writing-retro` 复盘迭代规则库：
  `python .agents/skills/writing-retro/scripts/retro_ledger.py snapshot --scene "<场次名>" --file "<场景文件路径>"`（未落盘用 `--stdin`）。
- 正文有实质修改（新写、重写、清理、按正文待改修改），该场 `status` 改为 `written`；完成「正文待改」即删对应条目，保留空小节。

## 场景卡与 SceneNotes

| 位置 | 写什么 |
| --- | --- |
| 场景卡 `synopsis` | 这场发生了什么、改变了什么，一两句（结果导向，不写经过与收尾） |
| 场景卡 `conflict` | 这场的戏剧矛盾，一句话（不复述事件经过） |
| 场景卡 `setup_scenes`／`payoff_scenes` | 伏笔、铺垫与兑现关系，两边都写（不另用文字重复） |
| SceneNotes `## 节拍` | 对剧情重要、不能随意改序的事件节点 |
| SceneNotes `## 边界` | 违反即造成实际逻辑错误的客观硬条件 |
| SceneNotes `## 正文待改` | 方案已改或与 Codex 冲突、正文尚未跟上的条目（常驻小节） |

- **节拍**：每条一句，不写动作、神态、道具和措辞；后场需呼应的关键台词可留原句。本场最该写足的一条末尾标「（重点）」，只标一条；没有就留空。
- **边界**：只写客观硬约束（如必须在变身冷却结束后发生）；没有就留空。
- **结构硬规**：SceneNotes 只留这三节，不加其他小节。
- **不写内容**：修改历史、方案比较、错误纠正、解释性描述、局部写法建议、可由 Codex 或前后场推出的约束；否定旧方案（如“不要让王倩已经进屋”）不是边界。
- 拿不准该不该留的条目，末尾标「（待审）」，不擅自删改。

```markdown
## 节拍

- 苏晚回到宿舍，碰见正在开门的王倩。
- 两人一起进屋。
- 舍友互相介绍。（重点）

## 边界

## 正文待改
```

## AI 沟通标准

- 初稿讨论与修改严格执行根目录 `AGENTS.md` 的局部修改铁律：未提及内容原样保留，只改明确指出的局部并仅输出替换片段。
- 回复简短、高效；除非用户主动询问，否则不做长篇解释。
- 禁止只发编号、序号或仅有标题；引用、确认或选择某一项时，须同时写明标题和关键内容，使回复脱离上文也能看懂。
- 回答任何涉及序号、编号、标号或排序的问题前，必须核查当前文件或系统的真实记录，不得凭记忆或旧对话推定。
