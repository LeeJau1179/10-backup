# 今生 Notes 文件夹规范

## 定位（铁律）

`Notes/` 是**作者私人参考工作区**，仅供作者自己备忘、打草稿、做决策。它不是设定层：

- **不被 Codex 索引，不是权威内容**——真正的权威只在 `Codex/`。
- 不直接生成正文，不改写 Scene；这里的内容服务作者决策，不直接进入成果层。

## 现有文件

| 文件 | 用途 |
| --- | --- |
| `本一卷一大纲.md` | 卷一时间线／排期，供撰写 scene 时参考 |
| `灵感.md` | 「已定 / 待补」的灵感与备忘，最随意 |
| `本一卷一其他内容.md` | 从大纲剥离的非大纲内容，按单一事实源逐条对照 Codex |

## 铁律

- **单向依赖**：Codex → Notes → Scene。本文**不写 scene 链接、不写 scene 名**，场景一律以事件描述指代；scene 改名、拆分、合并都不影响本文。
- **不复述机制**：奖金额度、结算口径、变身冷却与消耗等硬规则**一律以 Codex 为准**，本文只留 `[[wikilink]]` 指针，不得复述或改写。
- **冲突判定**：本文与 Codex 冲突时，**Codex 即答案，本文即错误**。
- **归位机制**：本文出现「Codex 尚未记录」的设定时，每条附「建议归位」指向应补进哪个 Codex 文件；纯剧情层内容（含具体日期、债务排期等）**留在 Notes，不回填 Codex**。
- 「待补 / 灵感」属作者 TODO，不自动转成 Codex 或 Scene，等作者指示再动。

## 修订来源标注

Notes 新增条目或修改条目的**实质内容**时，必须保留可追溯来源；这只是作者工作记录，不改变 Notes 非权威、不可直接驱动正文的定位。

- **逐条标注**：来源跟随具体条目或独立小节，而非仅在文件顶部统一注明。新增条目在该条目末尾写 `> 来源：作者修订`（或相应来源）。
- **来源选项**：`作者修订`、`GPT`、`DeepSeek`、`OpenCode`，以及其他可识别的模型／工具名称。作者明确提出的内容或改法记为 `作者修订`；AI 自主提出的方案记实际提出者，不因作者采纳而抹掉原来源。
- **来源与执行分开**：工具仅负责落盘时，不冒充建议来源。例如 GPT 提出、OpenCode 写入，记 `> 来源：GPT｜执行：OpenCode`。如已知 OpenCode 调用的具体模型，优先记录模型名称，`OpenCode` 作为执行工具；只有无法明确底层模型、且方案由 OpenCode 会话提出时，才可记 `OpenCode`。
- **后续修改追加记录**：保留原有 `来源`，在该条目下追加一条 `> 修订：YYYY-MM-DD｜来源：作者修订｜内容：简述改动`（将来源替换为实际来源；可附 `｜执行：OpenCode`）。同日不同修改可各留一条；不覆盖既有记录。
- **合作与确认**：多方共同提出时可写 `> 来源：GPT + DeepSeek`；作者仅确认 AI 建议时可增加 `> 状态：作者已确认`，不将原来源改为 `作者修订`。
- **不确定与例外**：来源无法核实时写 `待确认`，禁止猜测；纯格式整理、标点与错字修正可以不记录；不强制追溯已有 Notes 的历史来源。
- **作用范围**：仅约束 `今生/Notes/` 的内容文件；不把来源字段写进 Codex、Scene 或正文，也不覆盖 SceneNotes 的现有来源规则。

示例：

```markdown
### 林岚跟踪动机

通过刻意跟踪制造巧遇，主角并不知情。

> 来源：GPT｜执行：OpenCode
> 修订：2026-10-11｜来源：作者修订｜内容：明确苏晚不知情，取消探索全部秘密的动机
```
